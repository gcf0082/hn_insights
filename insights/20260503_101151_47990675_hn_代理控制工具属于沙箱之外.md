## 核心观点

本文探讨了 AI Agent（代理）的核心架构设计选择：**Agent Loop（代理循环）应该在沙箱内部还是外部运行**。

### 两种架构对比

| 特性 | 沙箱内架构 | 沙箱外架构 |
|------|-----------|-----------|
| Agent Loop 位置 | 与代码在同一容器内 | 在后端服务器运行 |
| 凭证管理 | 沙箱内 | 沙箱外（安全隔离）|
| 多用户场景 | 分布式文件系统问题 | 共享数据库方案 |
| 资源利用 | 常驻运行，无法暂停 | 可按需启用/暂停沙箱 |
| 持久化执行 | 需自行实现 | 依赖外部框架（如 Inngest）|

## 关键结论

### 1. 选择沙箱外架构的三大理由

**凭证安全**：API密钥、用户令牌、数据库访问权限都保存在沙箱外部，即使沙箱被攻破也没有可窃取的凭证。

**资源弹性**：可以在代理不需要执行命令时暂停沙箱（如 LLM 调用、等待 CI 等场景），仅在需要运行命令时才激活。

**多用户友好**：多个工程师共享同一组织下的技能和记忆时，可使用共享数据库而非分布式文件系统。

### 2. 需解决的技术挑战

- **持久化执行**：使用 Inngest 框架checkpoint每个步骤，确保代理会话在部署/故障后恢复
- **沙箱冷启动**：使用 Blaxel 实现25ms快速恢复
- **虚拟化文件系统**：路径分发到不同后端（/workspace/* → 沙箱，/skills/* 和 /memory/* → 数据库）

### 3. 遗留问题

- 需持续适配新发布的 Agent 模式（如子代理、计划、后台任务）
- Bash 工具可绕过虚拟化层访问真实文件系统
- 并发场景下的一致性问题仍未完美解决

## HN 热门评论摘要

**@tptacek**：存在其他模型，不需要沙箱。给代理一台隔离的计算机，使用 token 化凭证或代理处理 secrets。文章呈现了错误的二选一，暗示沙箱必须是短暂的，但实际上可以选择持久计算机并在不使用时停止计费。

**@jdw64**：有趣的现象是新技术出现时，人们竞争定义和拥有其标准。Manus 在六个月内重建了五次 harness，LangChain 一年内重新架构了四次 Deep Research，Mitchell Hashimoto 在二月份提到这个概念后掀起了"harness 工程"热。

**@zmmmmm**：真正的问题是 harness 进化太快，与 LLM 一样难信任。如果 harness 有 LLM 没有的能力，且 LLM 可以触发这些能力，实际上就构成了"致命三要素"之一。长期来看应该是独立的安全层，类似hypervisor。

## 总结与见解

本文是 Mendral 公司（来自 Docker 和 Dagger 的团队）基于实际生产经验的架构分享。对于构建多用户 AI Agent 系统具有重要参考价值：

1. **架构选择取决于使用场景**：单用户场景可用沙箱内方案简化，多用户场景建议沙箱外方案
2. **虚拟化文件系统**是平衡兼容性（使用模型训练的 API 表面）与灵活性的关键设计
3. **资源效率**在大规模部署时显著：按需激活沙箱可大幅降低成本

该文反映了 AI Agent 工程领域仍处于快速迭代阶段，架构最佳实践尚未定型。
