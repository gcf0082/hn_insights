## 核心内容摘要

本文作者分享了他在 AI 辅助软件开发过程中，如何通过编写结构化的 YAML 规范来克服"AI 精神病"（AI psychosis），并开源了一个名为 **Acai.sh** 的工具包。

### 核心观点

1. **规范必须存在**：无论是否书面化，规范都必然存在于团队的头脑或对话中。既然如此，不如现在就把它写下来。

2. **ACID 编号系统**：作者引入了"验收标准 ID"（Acceptance Criteria IDs），在代码中引用这些编号，以便追踪每个需求是否被实现和测试。

3. **YAML 格式优势**：使用 `feature.yaml` 格式比 Markdown 更结构化，便于 LLM 解析和控制上下文窗口。

### Acai.sh 工具包

- **feature.yaml**：简洁的规范模板，支持编号的需求列表
- **CLI 工具**：支持 CI 和 agent 集成
- **Web 仪表板**：查看实现状态、验收覆盖率

### 工作流程

1. **规范阶段**：用 YAML 编写功能规范
2. **交付阶段**：让 agent 读取规范并实现，代码中引用 ACID 编号
3. **审查阶段**：通过仪表板按需求审查，而非逐文件审查
4. **迭代**：修改规范或通过仪表板添加注释

## 社区反应分析

### 支持观点

- **beshrkayali**：AI 生成的代码缺乏"制度性记忆"，规范是将意图持久化的正确方式
- **gnat**：明确区分"需求"与"约束"，尊重现有系统架构
- **energy123**：用人类编写的规范作为输入，AI 生成中间规范，逐步扩展到最终代码
- **bonesss**：行为驱动开发（BDD）本质上也是将规范编码到代码库中

### 质疑观点

- **hansmayer**：质疑为何回归瀑布流程；批评缺乏实际数据支撑的结论
- **jFriedens**：文章标题说"克服 AI 精神病"，实际却是越陷越深
- **wesselbindt**：为何不直接写可执行规范？
- **zarzavat**：YAML 是最差的技术之一，充满缺陷

### 工具对比

社区提及的类似工具：
- **OpenSpec**：作者认为其描述"当前行为"而非"应该行为"
- **GitHub SpecKit**：被评价为"带额外步骤的氛围编程"
- **Kiro**：将 Markdown 转换为 EARS 语法
- **lat.md**：代码标注规范引用的工具

## 结论

这篇文章反映了 AI 辅助开发领域的一个重要趋势：**从"提示工程"向"规范驱动开发"演进**。作者认为，在 AI 生成代码的速度超过人类阅读速度的时代，验收测试和验证将成为瓶颈，而结构化的规范是解决这一问题的关键。

争议点在于：这种方法是真正的工程进步，还是另一种形式的技术仪式（technique theatre）？
