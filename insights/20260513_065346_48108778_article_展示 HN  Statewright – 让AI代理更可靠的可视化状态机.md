## 项目概述

Statewright 是一个为 AI 编程智能体提供状态机护栏的工具。它的核心思想是：**与其让模型更大，不如让问题更小**。

传统的 AI 智能体面临的问题是：给予模型 40+ 个工具和一个开放性问题，模型几乎无法完成任务。Statewright 通过状态机来约束工具和解决方案的空间，使模型在每个步骤中都能在专注的上下文中进行推理。

## 核心特性

### 1. 状态机工作流

Statewright 允许开发者定义工作流状态机和转换规则：

- **planning（规划）**：只允许使用 Read、Grep、Glob 等只读工具
- **implementing（实现）**：允许 Edit、Write 等编辑工具，同时限制 shell 访问
- **testing（测试）**：只允许特定的测试命令（如 pytest、cargo test）
- **completed（完成）**：最终状态

### 2. 护栏机制

| 护栏类型 | 功能描述 |
|----------|----------|
| **按状态工具限制** | 工具在不处于 `allowed_tools` 状态时对智能体不可见 |
| **Bash 辨别力** | 在非写入状态下阻止重定向（>>）、破坏性操作（rm、shred） |
| **编辑限制** | 拒绝超过 `max_edit_lines` 的 diff，限制每个状态编辑的文件数 |
| **命令白名单** | 按状态匹配允许的命令前缀 |
| **条件转换** | 基于上下文数据的程序化谓词（如 eq、gt、exists） |
| **审批门控** | `requires_approval` 在高风险转换前暂停等待人工审查 |
| **环境作用域** | 每个状态的 `blocked_env` 和 `env_overrides` |

### 3. 支持的智能体

| 智能体 | 集成方式 | 强制执行 |
|--------|----------|----------|
| Claude Code | Hooks + MCP | 强制（协议层） |
| Codex | Hooks | 强制（Alpha） |
| opencode | TypeScript 插件 | 强制（Alpha） |
| Pi | Skills 扩展 | 强制（Alpha） |
| Cursor | MCP + rules | 建议性（Alpha） |

## 研究结果

| 模型 | 大小 | Bug Fix (26行) | SWE-bench (5任务) |
|------|------|----------------|-------------------|
| gemma3 | 3.3GB | FAIL | FAIL |
| gemma4:e2b | 7.2GB | PASS* | FAIL |
| gpt-oss:20b | 13.8GB | PASS | PASS (5/5) |
| gemma4:31b | 19.9GB | PASS | PASS (5/5) |
| llama3.3 | 42.5GB | PASS | PASS (2/2)† |

*\*带 specialized edit_line tool adaptation*
*†在初始实验运行后测试了 5 个任务中的 2 个*

关键发现：在本地模型上，13.8GB 和 19.9GB 的模型从 **2/10 提升到 10/10**，使用相同的任务和硬件。13GB 以下的模型可以产生工具调用，但无法保留足够的文件内容来产生准确的编辑。

## 使用方法

### 快速开始（Claude Code）

```bash
/plugin marketplace add statewright/statewright
/plugin install statewright
```

然后启动工作流：

```
start the bugfix workflow
```

或使用斜杠命令：

```
/statewright start bugfix
```

### 工作流示例

```json
{
  "id": "bugfix",
  "initial": "planning",
  "states": {
    "planning": {
      "allowed_tools": ["Read", "Grep", "Glob"],
      "max_iterations": 8,
      "on": { "READY": "implementing" }
    },
    "implementing": {
      "allowed_tools": ["Read", "Edit", "Write"],
      "max_edit_lines": 20,
      "max_files_per_state": 3,
      "on": { "DONE": "testing" }
    },
    "testing": {
      "allowed_tools": ["Read", "Bash"],
      "allowed_commands": ["pytest", "cargo test", "npm test"],
      "on": {
        "PASS": { "target": "completed", "guard": "tests_passed" },
        "FAIL_TEST": "implementing"
      }
    },
    "completed": { "type": "final" }
  },
  "guards": {
    "tests_passed": { "field": "test_result", "op": "eq", "value": "pass" }
  }
}
```

## 技术架构

- **核心引擎**：Rust 编写，无运行时依赖，可嵌入使用
- **插件层**：通过 MCP 与智能体集成
- **自托管**：引擎（`crates/engine`）采用 Apache 2.0 许可证，可免费自托管

---

## 权衡与局限

- 需要智能体支持 MCP（或 Codex 的 Hooks）
- 工作流定义需要手动编写，但可以通过 `statewright_create_workflow` 由智能体生成
- Cursor 的强制执行是建议性的，而非强制的
- 研究结果基于 5 任务的 SWE-bench 子集，非完整的 2294 实例基准
- 如果工作流过于限制，智能体会卡住，`statewright_deactivate` 是脱困 hatch

---

## 总结

Statewright 提供了一种优雅的解决方案来解决 AI 智能体的"脆弱性"问题。通过状态机护栏，它能够：

1. **减少上下文窗口压力**：模型只看到当前阶段需要的工具
2. **防止灾难性操作**：在协议层阻止危险操作
3. **提升推理质量**：更小的工具空间使模型能够真正推理而非盲目尝试
4. **支持多种智能体**：广泛兼容主流 AI 编程工具

对于希望提升 AI 智能体可靠性和效率的开发者来说，Statewright 是一个值得关注的项目。
