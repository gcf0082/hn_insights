## 核心内容

Ben Cochran（前 NVIDIA、AMD 工程师，担任 Distinguished Engineer 超过 20 年）发布了 Statewright——一个通过视觉状态机让 AI 代理变得可靠的开源工具。

### 问题与解决思路

当前代理问题解决方式非常脆弱。作者认为，要让代理可靠工作，要么需要 massive 参数数量，要么需要 massive 上下文窗口来保持解决方案空间可用。大多数人通过更大的模型和更长的提示来强制实现可靠性。

作者采用了不同的思路：**不是让模型变大，而是让问题变小**。他使用较小的模型（13-20B 参数范围），让它们解决真实的 SWE-bench 问题。通过使用形式化状态机约束工具和解决方案空间：

- 每个状态定义模型可以访问哪些工具
- 每个状态限制迭代次数
- 定义有效的转换路径
- 规划状态只给读工具
- 实现状态给编辑工具（限制范围防止大规模修改）和友好的 bash 工具
- 测试状态只允许测试命令
- 模型无法跳过步骤或在错误时间使用错误工具

### 研究发现

实验结果比预期更令人鼓舞：

1. **参数门槛**：在 13B 参数以上，多个模型系列（qwen-coder、gpt-oss、gemma4）都有一致的改进
2. **低于 13B 的模型**：可以导航状态机，但无法保留足够上下文来产生准确的编辑
3. **前沿模型也受益**：Haiku 和 Sonnet 开始超越其参数表现，Opus 解决更可靠，使用更少 token，减少死亡螺旋
4. **微调无效**：微调没有产生这类功能性改进
5. **关键洞察**：上下文窗口利用率比原始上下文大小更重要——每一步的紧密作用域工作上下文优于模型对所有内容的不受限制访问

### Statewright 核心特性

- **Rust 引擎**：评估状态机定义（状态、转换、守卫、工具限制）
- **编排层**：不使用 LLM，强制执行状态机
- **插件层**：通过 MCP 集成 Claude Code（即将支持 Codex、Cursor）
- **工作流程**：激活工作流程时，自动执行每状态的守卫rails
- **视觉编辑器**：在 statewright.ai 上可以图形化编辑工作流程

## 社区观点

### 积极评价

- **创新方法**：评论者对用状态机约束 LLM 的方法表示赞赏
- **实用性**：免费层可供尝试，集成 Claude Code 方便易用
- **理论支持**：有评论指出这与 "liquid neural networks" 等自适应计算思想有关联

### 技术讨论

- **实现细节**：有人询问具体如何强制执行状态机（通过协议而非提示）
- **与 DAG 的区别**：状态机不是 DAG，它们有循环和重试，这正是代理工作实际需要的
- **失败路径可视化**：视觉编辑器可以清晰看到失败路径、重试循环和审批门

## 结论

Statewright 提出了一种创新的方法来提高 AI 代理的可靠性。与其依赖更大的模型和更长的上下文窗口，不如通过确定性代码（形式化状态机）来约束非幂等的 LLM。这种方法的关键洞察是：**上下文窗口利用率比原始上下文大小更重要**。通过在每个步骤提供紧密作用域的工作上下文，模型可以更可靠地执行任务，同时减少"死亡螺旋"和token浪费。该工具现已提供免费层可通过 MCP 集成到 Claude Code 中使用。
