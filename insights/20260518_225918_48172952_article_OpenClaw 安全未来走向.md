## 报告摘要

本文阐述了 OpenClaw 在安全领域的发展方向，强调在保持强大功能的同时，建立更清晰的边界和更强的可审计性。OpenClaw 能够读取文件、运行命令、安装插件、访问网络，并在真实机器上为真实用户服务。这种强大的能力虽然常被描述为危险，但 OpenClaw 致力于使其变得可管控、可审计，而非盲目无界。

## 核心安全方向

### 1. 文件系统边界与 fs-safe

OpenClaw 运行在用户机器上，能够访问文档、代码库和照片等文件。最常见的文件系统风险是路径遍历，但这只是更大类问题的一个症状：边界不清晰。代码原本想在某个目录下操作，却可能因符号链接、绝对路径、归档解压或拼接错误而跨越到其他目录。

**fs-safe** 是 OpenClaw 开发的安全文件系统模式集合，已将安全模式整合为共享库，使核心代码、插件和相邻服务都能使用相同的根边界原语。这不是沙盒，但能防止文件系统代码中的边界穿越错误。

**技术细节**:
- 插件工作区内的写入操作正常执行
- 遍历和绝对路径写入超出工作区范围时会被拒绝并返回 "outside-workspace" 错误

**下一步计划**: 将这些原语作为 ClawHub 上插件的预期模式，绕过这些检查虽不自动视为恶意，但具有安全相关性，长期应影响插件的信任评分。

**运行时状态重构**: 最安全的文件系统调用仍是不调用。SQLite 运行时状态重构正在推进中，会话、转储、调度器状态和插件状态将存入类型化数据库，具有清晰的所有权和事务，而非松散的文件。

### 2. 网络出口与 Proxyline

代理系统使 SSRF（服务器端请求伪造）比普通 Web 服务更难防范。在普通服务中，用户控制的 URL 往往是例外；而在代理运行时，用户控制或模型影响的 URL 是正常产品行为。

**现有方案不足**: URL 验证不足以解决问题。验证时解析 DNS，获取时再次解析，两者之间答案可能改变。验证时指向公网 IP 的主机可能在请求发出时指向元数据端点。

**Proxyline 解决方案**: 这是一个 Node 进程路由层，安装进程级路由来覆盖 Node 网络表面，并通过配置的代理发送流量。连接时策略应存在于代理层面：阻止元数据地址、私有范围、环回陷阱和环境所需的其他内容。

**功能特点**:
- 代理负责路由，代理策略负责执行
- 为运维人员提供可观测性，可通过已信任的基础设施监控目标、速率和阻止尝试
- 验证路径：example.com 应通过，环回陷阱应失败

**局限性**: 原始套接字、本机模块、异常传输、早期捕获的代理和非 OpenClaw 子进程仍可能绕过 Node 级防护。

### 3. ClawHub 插件信任

ClawHub 作为插件信任和来源的权威，当插件来自 ClawHub 时应消费这些信号，而非仅在安装后依赖本地检查。

**ClawHub 管道信号**:
- ClawScan、VirusTotal、静态分析、元数据检查、来源追溯和人工审核
- 各有各的噪音，管道对所有内容尖叫会导致用户学会忽略

**信任证据机制**: ClawHub 可为特定包版本附加信任证据，说明该版本是干净、可疑、待定、隔离、撤销还是恶意。可为恶意或隔离版本阻止下载，并向用户展示变化及原因。

**插件来源**: 插件可来自 GitHub、私有仓库或文件传递，这一模式不会消失。用户拥有自己的机器，OpenClaw 不应假装这不是事实。

**安全路径优化**: 发布到 ClawHub、获取扫描、附加证据，让用户在安装前权衡这些证据。

**高信任层级**: 正在探索官方包、受信任发布者和更严格审核的更高信任层级。对于 ClawHub 之外的插件，也希望扫描能覆盖，但具体产品形态仍需打磨。

**安全基准**: 如果 ClawHub 将版本标记为恶意和隔离，ClawHub 安装路径应拒绝安装。

### 4. 命令审批与提示疲劳

用户收到的提示快到无法阅读。几分钟后，用户会启用 YOLO 模式以继续工作，此时提示训练的是用户停止阅读。

**解决方向**: 更少的提示，更好的提示。

**准确性改进**: 解析层面的改进正在进行。字符串匹配不足，如果允许或阻止列表只看外层命令，包装器就会成为绕过手段。理解 `rm` 但无法看穿 `bash -c "rm -rf ~/something"` 的策略不是用户应信任的策略。

Shell 审批路径现已评估常见 shell `-c` 包装器的内部命令链。如果内部链包含不允许的可执行文件，包装器不应使其安全。命令高亮器也使用 Tree-sitter 来展示 OpenClaw 在包装器内发现的内容。

**PowerShell 支持**: 有其独特的陷阱，对于不理解的表单闭门失败，更广泛的支持正在规划中。

**更难的半部分**: 决定何时提问。静态审批策略要么对所有可能风险提示，要么依赖固定的允许/拒绝列表，无法判断命令是否适合当前任务。

**用户真正关心的问题**: 我是否希望这件事发生？

**上下文审批实验**: 目标不是"从不提示"，而是提示有意义——当有意义时，用户应该停下来阅读。

**OpenAI 用户**: 暴露 Auto Review 功能，这是代码库特定的特性，用单独的审查代理替换 sandbox 边界的人工审批。

### 5. 静态分析

OpenClaw 收到过大量 GitHub 安全公告（GHSA）。首要任务是堵住漏洞，其次是确保同一 bug 类别不会再次出现。

**修复后工作**: 公告后很容易认为完成，但 GHSA 是关于 bug 类别的证据，而非单个 bug。分类后的问题是：能找到所有看起来像这样的代码吗？

**解决方案**: 使用 OpenGrep 和精确规则包。每个规则绑定到一个公告、报告或审查发现。基线目标是回归检测：相同脆弱形态返回时，CI 在审查前捕获。更好的目标是变体检测：捕获同一错误的附近版本。

**精度重要性**: 嘈杂的规则比没有规则更糟，因为会教导团队忽略该渠道。

**当前状态**: 已提交精确的 OpenGrep 规则包包含 148 条规则，在 PR 差异上运行，可手动运行完整扫描。新修复的公告成为新规则的候选。

**CodeQL 配合**: 用于更深的语义覆盖，运行更慢且维护更嘈杂，两者配合使用。

## 对 OpenClaw 用户的意义

OpenClaw 不会变得更弱，而是在建立更容易看到和防御的边界。

不会承诺无风险的代理。任何这样承诺的人要么在推销什么，要么还没出货足够多。

能够承诺的是方向：OpenClaw 可以在保持强大的同时变得更加可防御。这正是团队正在构建的方向。
