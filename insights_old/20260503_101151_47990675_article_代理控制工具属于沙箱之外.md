## 内容摘要

本文探讨了 AI Agent（代理）的核心架构问题：Agent 驱动循环（harness）应该运行在沙箱内部还是外部。作者来自 Mendral 公司，他们选择了"沙箱之外"的架构，并详细解释了原因及实现方案。

---

## 核心概念

### 什么是 Agent Harness？

Agent harness 是驱动 LLM 的循环机制：
1. 发送提示词
2. 获取响应
3. 执行模型请求的工具调用
4. 将结果反馈给模型
5. 重复直到模型表示完成

每个生产级 Agent 都包含这一机制，区别在于它运行在哪里。

### 两种架构对比

| 特性 | Harness 在沙箱内 | Harness 在沙箱外 |
|------|------------------|------------------|
| 循环位置 | 与代码同处一个容器 | 运行在后端服务器 |
| 凭证存储 | 在沙箱内（不安全） | 后端保留（安全） |
| 多用户支持 | 需要解决分布式文件系统问题 | 共享数据库 |
| 沙箱生命周期 | 与会话绑定，无法暂停 | 可按需挂起/恢复 |

---

## 选择"外部架构"的原因

### 1. 凭证安全

- LLM API 密钥、用户令牌、数据库访问权限都保存在沙箱外部
- 沙箱只包含 Agent 工作所需的环境
- Agent 无法逃逸到敏感资源

### 2. 沙箱可挂起

- Agent 大部分时间不需要沙箱：思考、调用API、总结、等待CI
- 只有执行命令时才需要沙箱
- 可显著降低成本

### 3. 多用户场景

- 多位工程师共享技能（skills）和记忆（memories）
- 外部架构将状态存储在共享数据库
- 避免分布式文件系统问题

---

## 三大技术挑战及解决方案

### 1. 持久化执行（Durable Execution）

**问题**：Agent 会话可能运行数小时，必须能经受住部署、扩展和故障。

**解决方案**：使用 Inngest（他们自创的 CI 摄取管道也在用）
- 每个回合是一个 step
- Inngest 会为每个 checkpoint
- 服务重启后从断点继续

### 2. 沙箱生命周期管理

**问题**：冷启动需要数秒，对交互式使用来说太长。

**解决方案**：使用 Blaxel
- 25毫秒从待机恢复
- Agent 不执行命令时挂起沙箱
- 执行时立即恢复

### 3. 文件系统虚拟化

**问题**：
- Agent 需要访问技能文件、记忆文件、子代理、计划等
- 这些在本地文件系统假设下设计（`.claude/skills/foo.md`）
- 沙箱是可销毁的，状态不能保存在沙箱内

**解决方案**：单一接口，两个后端
- 虚拟化文件系统访问
- `/workspace/*` → 沙箱
- `/skills/*` 和 `/memory/*` → Postgres 数据库
- Agent 感知不到区别

## 保持原 API 表面的重要性

### 为什么虚拟化优于新增工具？

1. **注意力分散**：更多工具意味着每个工具获得的注意力减少
2. **提示词膨胀**：工具数量影响提示词长度
3. **训练路径**：前沿模型的强化学习是基于 Claude Code 风格的 API 训练的（`read(path)`, `write(path, content)`, `edit(path, old, new)`）
4. **自定义工具偏离训练轨迹**：模型表现可能不如原生接口

### Bash 泄漏问题

- Agent 的 bash 工具会绕过虚拟化层
- 解决方案：系统提示词警告 + 用 tree-sitter 解析 bash 调用

---

## 仍待解决的难题

1. **SOTA 快速演进**：新模式（子代理、计划、后台任务）不断出现，通常假设本地文件系统
2. **路径前缀风险**：使用与 Claude Code 相同的路径布局，未来可能需要迁移
3. **一致性**：多会话并发更新记忆时的冲突解决，目前采用"最后写入胜出"

---

## 关键要点

1. **多用户场景**是架构选择的关键考量
2. **凭证安全**是外部架构的首要优势
3. **文件系统虚拟化**是多用户场景的必备方案
4. **保持与训练一致的 API 表面**能获得最佳模型表现
