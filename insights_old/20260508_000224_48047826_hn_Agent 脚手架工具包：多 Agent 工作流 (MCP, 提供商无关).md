## 项目概述

Agent-harness-kit (AHK) 是一个用于多代理工作流程的脚手架工具，具有以下特性：
- MCP (Model Context Protocol) 支持
-Provider-agnostic (provider 无关)
- 专为构建多代理系统而设计

## 核心讨论话题

### 1. 流程定义灵活性

用户 `philipp-gayret` 提出关键问题：现有脚手架大多是 "build -> review" 这种简单流程，能否定义更复杂的流程？例如：
- 对每个 review 发现执行特定操作 X
- 从端到端测试回溯到构建步骤

项目作者 `Fiahil` 回应存在 "observe" 步骤：当项目部署后，会观察实际发生的情况与规格说明的差异并进行调和。随着脚手架工具的普及，预计会出现更多流程变体。

### 2. 子代理工作完成证明

核心问题：子代理如何不可否认地证明其工作已完成？
- "lead-agent" 仅查看输出是否足够？
- 这是否会使 lead-agent 成为隐式审查者？
- 是否需要后置条件检查？

用户 `dubovskiyIM` 提出：系统是基于类型化状态还是原始输出进行推理？这是 LLM 判断approval作为最终关卡的关键问题。

### 3. 自动化工作树创建与沙箱化

用户 `elysianfields` 分享了自己的方案：
- 使用 git worktrees 创建独立空间
- 通过符号链接 .env 文件
- 使用 bubblewrap 隔离工作树
- 支持单个代理同时处理多个任务

### 4. 代理间通信层

用户 `eugeniecregan` 正在开发让代理之间以及不同团队代理之间通信的层：
- GitHub: https://github.com/awebai/aweb

用户 `mettamage` 实现了一个简单的通信层，并指出：
- 某些内容不应放入特定上下文中
- 角色更多，更灵活，但速度稍慢

有趣发现：代理会发展出"个性"，有时甚至会互相表现出轻微的被动攻击性。

### 5. 类型化状态传递

用户 `arctide` 分享了关键经验：
- 代理被告知做某事后，下一步只有状态标记为"posted"时才相信完成
- "ready_to_post" 或 "draft_verified_awaiting_review" 实际上是错误状态

关键技巧：需要定义多种"非预期"状态：
- `blocked_quota` (配额blocked)
- `blocked_no_credentials` (无凭证)
- `skipped_anti_bunching` (跳过)

核心观点：AHK 的类型化传递是正确的原语 Discipline：代理从不写半状态，每次运行都以文档化的终态结束（成功或其他）。

### 6. Provider 相关性

用户 `lynellf` 质疑：虽然声称 provider-agnostic，但实际只看到 Claude Code 和 OpenCode 作为示例。与 RooCode 等类似工具的区别是什么？

作者未直接回应此问题。

## 关键洞察

1. **类型化状态传递**: 代理工作流应使用类型化状态传递而非原始输出，确保每次运行都有明确的终态
2. **沙箱隔离**: git worktrees + bubblewrap 是隔离代理工作区的有效方案
3. **代理个性**: 多代理系统可能出现代理发展出个性的现象，需要通过系统提示词约束
4. **错误处理**: 需要定义多种 blocked/失败状态，防止无限重试造成的资源浪费
5. **Provider 无关性**: 真正的 provider-agnostic 需要支持多种 LLM Provider，而不仅仅是示例中的几个
