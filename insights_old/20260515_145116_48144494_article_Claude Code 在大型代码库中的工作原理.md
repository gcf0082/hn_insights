## 摘要

Claude Code 已在生产环境中运行于数百万行代码的单体仓库、数十年历史的遗留系统、跨越数十个仓库的分布式架构，以及拥有数千名开发者的组织中。这些环境面临着小型简单代码库所不具备的挑战。本文总结了在大规模部署中导致 Claude Code 成功采用的模式，为考虑采用 Claude Code 的团队提供了良好的起点。

## 一、Claude Code 如何在大型代码库中导航

Claude Code 导航代码库的方式与软件工程师相同：遍历文件系统、读取文件、使用 grep 查找所需内容，并在代码库中跟踪引用。它在开发者的本地机器上运行，不需要构建、维护或上传代码库索引。

传统的 AI 编码工具依赖基于 RAG 的检索，通过嵌入整个代码库并在查询时检索相关片段。在大规模场景下，这些系统可能会失败，因为嵌入管道无法跟上活跃的工程团队。当开发者查询索引时，它反映的是代码库在数天、数周甚至数小时前的状态。检索返回的是团队两周前重命名的函数，或者引用的是一个在上个 sprint 中删除的模块，没有任何迹象表明这些内容已过时。

代理搜索避免了这些失败模式。没有需要维护的嵌入管道或集中索引，因为数千名工程师正在提交新代码。每个开发者的实例都基于实时代码库工作。但这种方法有一个权衡：当 Claude 有足够的起始上下文知道去哪里查找时，效果最好。这意味着 Claude 导航的质量取决于代码库的设置程度，通过 CLAUDE.md 文件和技能来分层上下文。如果要求它在数十亿行代码库中查找模糊模式的所有实例，工作开始前就会触及上下文窗口限制。投资于代码库设置的团队会看到更好的结果。

## 二、模型的重要性与生态系统

关于 Claude Code 最常见的误解之一是其能力仅由使用的模型定义。团队关注模型的基准测试及其在测试任务中的表现。实际上，围绕模型构建的生态系统（称为"harness"）比模型本身更能决定 Claude Code 的表现。

Harness 由五个扩展点构建：CLAUDE.md 文件、hooks、技能、插件和 MCP 服务器，每个都有不同的功能。团队构建它们的顺序很重要，因为每一层都建立在之前的基础上。另外两个功能（ LSP 集成和子代理）完善了设置。

**CLAUDE.md 文件是第一位的**。这些是 Claude 在每个会话开始时自动读取的上下文文件：根文件用于全局视图，子目录文件用于本地约定。它们赋予 Claude 完成任何事情所需的代码库知识。因为它们在每个会话中加载，无论任务是什么，保持它们专注于广泛适用的内容将防止它们成为性能负担。

**Hooks 使设置能够自我改进**。大多数团队将 hooks 视为防止 Claude 做错事的脚本，但它们更有价值的用途是持续改进。stop hook 可以反思会话期间发生的情况，并在上下文新鲜时提出 CLAUDE.md 更新。start hook 可以动态加载团队特定的上下文，这样每个开发者都能获得正确的模块设置，而无需手动配置。对于 lint 和格式化等自动化检查，hooks 以确定性的方式强制执行规则，比依赖 Claude 记住指令产生更一致的结果。

**技能让正确的专业知识按需可用，而不会膨胀每个会话**。在拥有数十种任务类型的大型代码库中，并非所有专业知识都需要出现在每个会话中。技能通过渐进式披露解决这一问题，卸载专门的工作流程和领域知识，否则这些知识会争夺上下文空间，并且仅在任务需要时加载。例如，当 Claude 评估代码中的漏洞时，安全审查技能会加载；而当代码更改需要更新文档时，文档处理技能会加载。

技能也可以绑定到特定路径，这样它们仅在代码库的相关部分激活。拥有支付服务的团队可以将他们的部署技能绑定到该目录，因此当有人在单体仓库的其他地方工作时，它永远不会自动加载。

**插件分发有效的设置**。大型代码库的挑战之一是好的设置可能停留在部落层面。插件将技能、hooks 和 MCP 配置捆绑到单个可安装包中，因此新工程师在第一天安装该插件时，他们将立即拥有与已经使用 Claude 的人相同的上下文和能力。插件更新可以通过托管市场在整个组织中分发。

例如，一个与之合作的大型零售组织构建了一个将 Claude 连接到其内部分析平台的技能，以便业务分析师可以在不离开工作流程的情况下提取性能数据。他们在向业务部门广泛推广之前将其作为插件分发。

**语言服务器协议（LSP）集成赋予 Claude 与开发者在其 IDE 中相同的导航能力**。大多数大型代码库 IDE 已经有一个 LSP 在运行，为"转到定义"和"查找所有引用"供电。向 Claude 公开这一点赋予它符号级精度：它可以跟随函数调用到其定义，跨文件跟踪引用，并区分不同语言中同名的函数。没有它，Claude 只会进行文本模式匹配，可能会定位到错误的符号。一家与之合作的企业软件公司在 Claude Code 推广之前就部署了全组织范围的 LSP 集成，专门是为了在规模上使 C 和 C++ 导航可靠。对于多语言代码库，这是最高价值的投资之一。

**MCP 服务器扩展一切**。MCP 服务器是 Claude 连接到无法直接访问的内部工具、数据源和 API 的方式。最复杂的团队构建了 MCP 服务器，将结构化搜索公开为 Claude 可以直接调用的工具。其他人将 Claude 连接到内部文档、票务系统或分析平台。

**子代理将探索与编辑分开**。子代理是一个孤立的 Claude 实例，有自己的上下文窗口，接受任务，完成工作，然后仅将最终结果返回给父代理。一旦 harness 到位，一些团队会启动一个只读的子代理来映射子系统并将发现写入文件，然后让主代理根据完整情况进行编辑。

## 三、成功部署的三个配置模式

如何为大型代码库配置 Claude Code 很大程度上取决于该代码库的结构。尽管如此，我们观察到的部署中有三种模式一致出现。

### 3.1 使代码库在大规模下可导航

Claude 在大型代码库中提供帮助的能力受限于其找到正确上下文的能力。太多上下文加载到每个会话中会降低性能，而太少上下文会让 Claude 盲目导航。最有效的部署会在使代码库对 Claude 可读性方面进行前期投资。一致出现的模式包括：

- **保持 CLAUDE.md 文件精简和分层**。Claude 在代码库中移动时_additively加载它们：根文件用于全局视图，子目录文件用于本地约定。根文件应该只是指针和关键陷阱；其他一切都会变成噪音。
- **在子目录而非仓库根目录初始化**。Claude 在与任务实际相关的代码库部分中作用域时效果最好。在单体仓库中，这可能感觉反直觉，因为工具通常假设根访问，但 Claude 会自动遍历目录树并加载沿途找到的每个 CLAUDE.md 文件，所以根级上下文永远不会丢失。
- **按子目录作用域化测试和 lint 命令**。当 Claude 只更改了一个服务时，运行完整套件会导致超时，并浪费上下文在无关输出上。子目录级别的 CLAUDE.md 文件应该指定适用于该部分代码库的命令。这在面向服务的代码库中效果很好，每个目录都有自己的测试和构建命令。在具有深层跨目录依赖的编译语言单体仓库中，按子目录作用域化更难实现，可能需要特定于项目的构建配置。
- **使用 .gitignore 文件排除生成的文件、构建工件和第三方代码**。在 `.claude/settings.json` 中提交 permissions.deny 规则意味着排除是版本控制的，因此团队中的每个开发者都获得相同的噪音减少，而无需自己配置。在某些代码库中，生成的文件本身就是开发工作的主题。从事代码生成器的开发者可以在本地设置中覆盖项目级排除，而不影响团队的其他成员。
- **当目录结构不能完成工作时，构建代码库地图**。对于代码不在传统目录结构中的组织，在仓库根目录放置一个轻量级 markdown 文件，列出每个顶级文件夹及其包含内容的单行描述，为 Claude 提供了它可以在打开文件之前扫描的目录表。对于有数百个顶级文件夹的代码库，这最好作为分层方法：根文件仅描述最高级结构，子目录 CLAUDE.md 文件提供下一级细节，在 Claude 在树中移动时按需加载。对于更简单的案例，@提及 Claude 应该引用的特定文件或目录也可以完成相同的工作。
- **运行 LSP 服务器，让 Claude 按符号而非字符串搜索**。在大型代码库中 grep 一个常见函数名会返回数千个匹配，Claude 会消耗上下文打开文件来弄清楚哪个重要。LSP 仅返回指向相同符号的引用，因此过滤发生在 Claude 读取任何东西之前。设置这需要为你的语言安装 code intelligence 插件和相应的语言服务器二进制文件；Claude Code 文档涵盖了可用插件和故障排除。

### 3.2 主动维护 CLAUDE.md 文件

随着模型的发展，为当前模型编写的指令可能会与未来的模型相冲突。引导 Claude 度过它曾经挣扎的模式的 CLAUDE.md 文件可能在下一个模型发布后变得不必要或积极限制。例如，一个告诉 Claude 将每个重构分解为单文件更改的 CLAUDE.md 规则可能帮助早期的模型保持在轨道上，但会阻止更新的模型进行它处理良好的协调跨文件编辑。

为补偿特定模型限制而构建的技能和 hooks，无论是模型推理还是 Claude Code 本身的工具，一旦这些限制不再存在，就会成为开销。例如，一个拦截文件写入以在 Perforce 代码库中强制执行 p4 edit 的 hook 在 Claude Code 添加原生 Perforce 模式后变得冗余。

团队应该期望每三到六个月进行一次有意义的配置审查，但在重大模型发布后性能感觉停滞不前时也值得做一个。

### 3.3 为 Claude Code 管理和采用分配所有权

仅靠技术配置不会推动采用。成功做的组织也在组织层面进行了投资。

推广最快的部署在广泛访问之前有专门的基础设施投资。一个小团队，有时甚至一个人，接好工具以便 Claude 在开发者第一次接触时已经适合他们的工作流程。在一家公司，几位工程师构建了一套插件和 MCP，在第一天就可用。在另一家公司，一个专注于管理 AI 编码工具的团队在推广开始之前就准备好了基础设施。在这两种情况下，开发者的第一次体验是高效的而不是令人沮丧的，采用从这里传播开来。

做这项工作的团队今天往往位于 developer experience 或 developer productivity 之下，这通常是负责新工程师入职和构建开发者工具的职能。在几个组织中出现的一个新兴角色是 agent manager：一个专注于管理 Claude Code 生态系统的混合 PM/工程师职能。对于没有专门团队的组织，最低可行版本是一个 DRI：一个人拥有 Claude Code 配置的所有权，有权对设置、权限策略、插件市场和 CLAUDE.md 约定做出决定，并负责保持它们的最新状态。

自下而上的采用会产生热情，但没有某人集中化有效的做法，它可能会碎片化。你需要一个人或一个团队来汇编和宣传正确的 Claude Code 约定（如标准化的 CLAUDE.md 层级或精选的技能和插件集）。没有这项工作，知识将保持部落化，采用将停滞不前。

在大型组织中，尤其是在受监管的行业，治理问题会提早出现，例如：谁控制哪些技能和插件可用，如何防止数千名工程师独立重建相同的东西，如何确保 AI 生成的代码经过与人类生成的代码相同的审查过程？为了及早解决这些问题，建议从一组已批准的技能、必需的代码审查流程和有限的初始访问开始，并在信心建立后扩展。

## 四、在你的组织中应用这些模式

Claude Code 围绕工程师是主要代码库贡献者、仓库使用 Git、代码遵循标准目录结构的传统软件工程环境设计。大多数大型代码库符合这种模式，但非传统设置（如大型二进制资产的游戏引擎、非标准版本控制或非工程师贡献代码库）需要额外的配置工作。我们的指导假设了一个传统设置，我们描述的模式在许多客户身上都有效。任何剩余的复杂性需要特定于你的代码库、工具和组织的判断。这就是 Anthropic 的 Applied AI 团队直接与工程团队合作将这些模式转化为你的组织具体要求的地方。
